> 狀態：**v0.1（定向）**　最後更新：2026-10-02

## 1. 風格定位

**休閒可愛的色鉛筆／蠟筆插畫風**，介於「兒童繪本塗鴉」與「寫實攝影」之間——保留正確的比例、透視與場景細節（建築結構、車輛、地形都站得住腳），但用溫暖手繪筆觸（排線、顆粒感）取代照片寫實感，整體調性溫馨、親切、不生硬。

**為什麼選這個方向**：
- 比純照片更「可愛休閒」，比純兒童塗鴉更「可信賴」——商場內容橫跨廟宇信仰（行修宮）、山林健行、在地老店飲食，需要一個既不失莊重、又不生硬官方的視覺語言。
- 用 AI 生成取代實景照片，同時解決「不想花時間實地拍照」與「網路既有照片版權」兩個問題（見下方第 6 節）。

## 3. 風格公式（可重複使用的生成提示詞模板）

之後生成新圖時，把下方模板中的 `[主體描述]` 換成對應場景即可，**其餘風格描述段落盡量維持原字不動**，以確保跨圖風格一致：

```
畫一張可愛休閒的蠟筆童書插畫風格圖片：[主體描述——場景、建築/地形、人物或物件、背景]。

風格要求：
- 可愛休閒的蠟筆/色鉛筆童書插畫風格
- 柔和的手繪筆觸質感，線條帶點不完美的手感，不要照片寫實，不要 3D 渲染
- 暖色調的大地色系：磚紅色、森林綠、溫暖米白/杏色背景、低飽和芥末黃點綴
- 柔和平面光線
- 寬幅橫向構圖，適合當網站 Banner
- 圖片內不要出現任何文字或浮水印
```

> **實作方式備註**：目前是透過 ChatGPT／Gemini 等消費端網頁版手動生成（非 API 自動化），每次生成建議同時附上 `行修宮廣場.png` 或 `停車場.png` 其中一張當「風格參考圖」一併上傳（如果生成工具支援圖片參考輸入），比純文字描述更能鎖定一致的筆觸與配色。

### 3.1 Logo 圖示提示詞

Logo 圖示跟情境插畫（Banner、景點圖）不同——需要「簡單、乾淨、可縮小辨識」，不能像場景圖那樣畫滿細節，所以用專門的 Logo 版提示詞，不套用上面的場景公式：

```
畫一個簡潔的品牌圖示（Logo mark），主題是台灣三峽白雞山區：
以簡化的山巒剪影為基礎（呼應白石垵山／雞罩山），
前景疊加一個簡化的廟宇屋頂剪影（呼應行修宮的飛簷造型），
整體造型單純、可辨識，不要畫滿整個畫面的複雜場景。

風格要求：
- 蠟筆/色鉛筆手繪質感，保留溫暖的筆觸排線，但整體造型要單純乾淨，不要碎細節
- 清楚的輪廓線，單一主體置中構圖
- 配色：磚紅色（屋頂／前景）、森林綠（山巒）、低飽和芥末黃點綴，背景為純白或透明
- 正方形構圖，圖示居中，四周留白
- 不要出現任何文字、不要浮水印
- 適合縮小使用在網站 Header，線條粗細不要過細
```

> 生成後的圖示屬於「Logo 的圖示部分」，仍需另外跟「三峽白雞觀光商場」文字（Logotype，字體見第 5 節）組合排版，才是完整 Logo。

## 5. 字體搭配

呼應插畫風格的「標題／內文」分工，字體也分兩種角色，不全站統一用同一套：

| 角色 | 字體 | 授權 | 說明 |
|---|---|---|---|
| 標題／強調文字 | **Chiron GoRound TC**（定案） | SIL OFL 1.1（免費可商用） | 圓體，筆畫圓潤，呼應插畫的手繪溫暖感；比 Hin 粉圓多出 10 種字重（ExtraLight～Heavy，含可變字型版本），排版彈性更高，已於 2026-10-05 確認在 Google Fonts 可正常載入並實際套用到前端專案 |
| 內文／機能性文字（交通時刻、設施清單、店家資訊等） | **Noto Sans TC** | SIL OFL 1.1（免費可商用） | 標準黑體，各字重齊全、瀏覽器相容性最穩，長文字與小字級的可讀性優於圓體，適合資訊密度高的頁面 |
| 英文／數字（店名、地址、電話等 Latin 字元） | 標題跟 **Quicksand**（圓體呼應），內文跟隨 Noto Sans TC 內建 Latin 字符即可 | Google Fonts，免費 | 不需要額外挑一套完整英文字體系統，避免過度複雜化 |

**取捨說明**：全站統一用圓體會更一致可愛，但會犧牲交通方式／設施清單等資訊型頁面的掃視效率；標題跟內文分工可以兩頭兼顧，代價是要多管理一套字型載入與切換邏輯。

**效能注意事項（重要）**：中文字型檔案通常很大（Noto Sans TC 全字集可能超過 10MB），本站使用 Angular SSR／Prerender（見 [02-網站架構(Sitemap)](../規格內容/02-網站架構(Sitemap).md)），上線前務必：
- 用 subsetting 工具（例如 `pyftsubset`）只打包網站實際會用到的字（繁體中文字數有限，常用字約 4000-5000 字即可覆蓋多數內容），不要整包 Noto Sans TC 全字集上線
- CSS 設定 `font-display: swap`，避免字型載入期間畫面空白（FOIT）
- 標題圓體字（Chiron GoRound TC）使用量遠小於內文黑體，檔案體積影響較小，但仍建議一併 subset

## 6. UI 元件造型語言

### 卡片（Card）

| 屬性 | 數值 | 說明 |
|---|---|---|
| `border-radius` | `20px` | 全站卡片統一圓角 |
| `box-shadow` | 最小範圍，例如 `0 1px 3px rgba(58, 51, 44, 0.06)` | 用 `--color-text`（暖色深灰）同色系的低透明度陰影，不用純黑陰影，避免看起來髒／生硬 |
| 背景 | `--color-surface` | 見第 4 節色票 |
| 邊框（選用） | `--color-border` 1px | 陰影極弱時，可用細邊框輔助卡片與背景的分隔感 |

### 按鈕（Button）

**圓角刻意跟卡片不同**——按鈕採**全圆角（pill／膠囊形，`border-radius: 9999px`）**，不沿用卡片的 20px。卡片是「內容容器」、按鈕是「可點擊的動作」，兩種圓角程度形成視覺層級，讓使用者一眼分辨容器與可互動元件；全圆角也更呼應 Hin 粉圓／Chiron GoRound TC 圓潤字體的調性。

| 類型 | 樣式 | 用途 |
|---|---|---|
| 主要按鈕（CTA） | `--color-primary` 實心填滿、文字米白 | 導航、規劃路線等主要動作 |
| 次要按鈕 | `--color-primary` 外框、文字同色、背景透明／極淡米色 | 次要動作 |

- **陰影**：維持最小範圍原則，靜止狀態極淡陰影（例如 `0 2px 4px rgba(58,51,44,0.08)`），互動回饋改用「顏色加深＋輕微位移」而非加重陰影——hover 背景轉 `--color-primary-muted` 並上移 1px，按下時歸位、陰影暫時消失，模擬按壓觸感
- **最小高度**：統一 `44px`（觸控熱區基本門檻）
- **外部連結按鈕**：站內多顆按鈕是「開新分頁連到站外」（Google 地圖、公車時刻表、店家官網等），文字後方統一加 ↗ 小圖示，呼應 [03-頁面內容規格](../規格內容/03-頁面內容規格.md) 全站共用元件一節既有的「外部連結標示」規則

**實作提醒**：專案使用 Angular Material，建議直接在 Material 的 theme tokens 層級（例如 M3 的 `--mdc-filled-button-container-shape`、`--mdc-filled-button-container-elevation` 等）統一覆寫，不要逐個元件手動加 CSS，才能全站一致套用、好維護。

### RWD 斷點

**單一斷點：`768px`（Tailwind 預設的 `md`），Mobile First**——不寫 media query 的基礎樣式即手機版，`768px` 以上套用 PC 版面。

- 只定一條線，不另外切平板層級：[03-頁面內容規格](../規格內容/03-頁面內容規格.md) 內所有 RWD 描述都是「PC／Mobile」二選一（商場店家 5 欄/2 欄、登山步道 4 欄/2 欄、分類篩選 button group/下拉選單等），沒有平板情境，不先為未要求的情境增加斷點數量
- **Tailwind 側**：直接用內建 `md:` 前綴，不客製斷點設定
- **Angular CDK 側**：涉及結構性切換（例如分類篩選 PC 用 button group、Mobile 改用 `mat-select`）需要用 `BreakpointObserver` 在 TS 判斷時，**自訂 query `(min-width: 768px)`，不要直接 import Material 內建的 `Breakpoints.Handset`／`Breakpoints.Tablet`**（預設切點是 599.98px／839.98px，跟 768px 對不齊，會讓 CSS 版面與 JS 結構切換的時機不同步）
- 若日後 768–1024px（平板直向）範圍卡片欄數顯得擁擠，可另外加 `lg:`（1024px）只調整欄數，不動結構邏輯，待實際套版出現問題再處理

## 8. 版權與生成注意事項

- 所有插畫**一律用文字描述生成（text-to-image）**，不把任何網路上找到的既有照片當 img2img 輸入來源——避免「風格轉繪仍視為衍生作品」的版權風險（細節見本文件所屬對話紀錄）。
- 若未來要大量批次生成（周邊景點、登山步道等十幾張圖一次補齊），建議改回 API 自動化流程（需在 Google Cloud 專案開通計費），目前先以消費端網頁版（ChatGPT／Gemini）手動生成兩張測試圖驗證風格方向。
- 每次生成後的圖檔建議統一存放在本資料夾（`設計風格/`），檔名採 `ref-編號-場景英文代稱.png` 格式，方便之後搬到 `前端/baiji-tourist-market-ui/public/assets/images/` 對應子目錄時可追溯來源。
