## 首頁 `/`（獨立頁面）

**目的**：作為全站的預設入口與回頭基地。使用者可以從任何頁面點擊 Header 左側的「三峽白雞觀光商場」Logo（圖示＋文字，整體可點擊）回到首頁，不需要透過主選單的任何一個項目。

**版面區塊（三塊，由上而下排列）**：

### 1. 輪播圖（Carousel／Banner）

商場代表性景觀照、行脩宮、白雞山景、活動主視覺輪播。

- **顯示方式**：一次顯示一張圖片，輪播切換。
- **最多張數**：5 張。
- **資料來源**：靜態圖片檔（放在前端 assets），圖片路徑清單直接寫成常數陣列，放在首頁元件的 `.ts` 檔案內（非外部 JSON 檔），格式為純字串陣列：

```ts
const bannerImages: string[] = [
  'assets/images/banner/banner-01.jpg',
  'assets/images/banner/banner-02.jpg',
  'assets/images/banner/banner-03.jpg',
];
```

- 陣列順序＝顯示順序，不做額外排序；若陣列超過 5 筆，僅取前 5 筆。
- **待確認／與既有規格的差異**：本次規格把輪播圖簡化為「純圖片路徑陣列」，不含連結欄位，和本文件原先「輪播圖可帶連結，導向活動頁／交通方式／商場介紹」的描述不同。先以此簡化版本為準；若日後需要恢復點圖跳轉功能，需把陣列格式升級為物件陣列（例如 `{ image: '...', link: '...' }`）。

### 2. 最新訊息公告

商場公告、行脩宮香期、步道封閉通知等即時性內容。

- **呈現方式**：橫向列表（horizontal list）。
- **排序**：依日期新到舊排序。
- **顯示筆數**：僅顯示最新 5 筆。
- **連結規則**：`link` 欄位有值才顯示為可點擊連結，點擊以新分頁開啟（`target="_blank"`）；無 `link` 則單純顯示文字，不可點擊。
- **資料來源**：常數陣列，寫在首頁元件的 `.ts` 檔案內（非外部 JSON 檔），格式為物件陣列：

```ts
interface NewsItem {
  createdAt: string;
  title: string;
  link: string;
}

const newsList: NewsItem[] = [
  {
    createdAt: '2026-10-10',
    title: '慶賀中華民國國慶日',
    link: 'https://www.google.com',
  },
  {
    createdAt: '2026-09-20',
    title: '中秋節營業時間調整公告',
    link: '',
  },
];
```

> 日期欄位建議統一用 ISO 8601 格式（`YYYY-MM-DD`），而非 `2026/10/10` 這種斜線格式——斜線格式在不同瀏覽器的 `Date` 解析行為不一致，容易讓排序結果不穩定。

### 3. 店家工商廣告（卡片輪播）

商場店家的促銷／廣告訊息區塊，用於導流到 `/shop`。本階段先建版位與元件，店家廣告內容待商場管理方或店家提供後補上。

- **呈現方式**：卡片輪播（card carousel）。
  - **PC**：一次顯示 4 張卡片。
  - **Mobile**：一次顯示 2 張卡片，且需支援觸控「按住拖動」（touch drag／swipe）切換。
- **卡片內容**：圖片＋標題（20 字以內）＋簡述（50 字以內）。
- **互動規則**：卡片有 `link` 時，點擊卡片以新分頁開啟連結；沒有 `link` 時點擊卡片不做任何動作（視覺上也不應呈現可點擊樣式，例如移除 hover/cursor-pointer 效果）。
- **資料來源**：常數陣列，寫在首頁元件的 `.ts` 檔案內（非外部 JSON 檔），格式為物件陣列：

```ts
interface ShopAd {
  title: string;
  link: string;
  image: string;
  brief: string;
}

const shopAds: ShopAd[] = [
  {
    title: '廣告標題',
    link: 'https://example.com',
    image: 'assets/images/shop/ad-01.jpg',
    brief: '簡述內容',
  },
];
```

> 20 字／50 字的字數限制建議由維護 `.ts` 常數陣列的開發者把關；前端可另外加 `line-clamp` + `text-overflow: ellipsis` 做保險，避免萬一超字數時版面跑掉。

### 技術建議：輪播套件選型

目前前端為 Angular 22（standalone components＋signals）＋ Angular Material＋Tailwind v4，首頁路由走 Prerender、最新訊息與工商廣告區塊走 Client 水合（見 [02-網站架構(Sitemap)](02-網站架構(Sitemap).md)）。在此前提下：

**建議：[Swiper](https://swiperjs.com/)（`swiper/element` Web Component 版本）**

- 一套套件可以同時滿足「輪播圖」（單張顯示）與「工商廣告」（多卡片、RWD 切換張數）兩種需求，不需要為了兩種輪播各自引入一個套件。
- 內建 `breakpoints` 設定，可直接宣告「≥1024px 顯示 4 張、<768px 顯示 2 張」，不用自己寫 media query 邏輯去控制一次顯示幾張卡片。
- 內建滑鼠／觸控拖曳（`grabCursor` + 觸控 swipe），開箱即滿足「mobile 要能按住拖動」的需求，不用額外刻手勢邏輯。
- 以原生 Web Component（Custom Elements）提供，需要在瀏覽器端呼叫一次 `register()`（建議包在 `afterNextRender` 或 `isPlatformBrowser` 判斷內，避免 SSR 階段因為 Node 環境沒有 `window`／`customElements` 而報錯），並在使用的 standalone component 加上 `schemas: [CUSTOM_ELEMENTS_SCHEMA]`（因為 `<swiper-container>`／`<swiper-slide>` 不是 Angular 元件）。
- Prerender 相容性：`<swiper-slide>` 內的 `<img>` 仍是一般的 light DOM 子元素，SSR 階段就會被渲染進 HTML，不會因為 Custom Element 還沒在瀏覽器端 upgrade 就消失——沒有 JS 的使用者或爬蟲仍看得到圖片內容，只是還沒有輪播切換行為，可接受。

**替代方案：[Embla Carousel](https://www.embla-carousel.com/)（core + `embla-carousel-autoplay` plugin）**

- 純 vanilla JS，沒有 Custom Element／Shadow DOM，輪播就是一般的 `<div>`／`<ul>` 結構，和現有 Tailwind＋Material 的樣式系統更好搭配，也不用處理 `CUSTOM_ELEMENTS_SCHEMA`。
- 核心體積更小（約 6KB），原生支援滑鼠與觸控拖曳。
- 缺點：沒有 Swiper 那種「宣告式 breakpoints＋同時顯示幾張卡片」的內建設定，需要自己寫版面 CSS（flex/grid＋overflow）並包一層 Angular 整合（`viewChild` + `afterNextRender`），整合工作量比 Swiper 多一些。

**不建議**：`ngx-slick-carousel`／`ngx-owl-carousel-o` 這類仰賴 jQuery／較舊生態的套件，與目前 standalone＋zoneless 風格、SSR 的新版 Angular 相容性與維護狀態都較弱；也不建議為了拿一個 Carousel 元件而額外引入 PrimeNG 整套 UI 元件庫，否則會變成同時維護 Angular Material＋PrimeNG 兩套元件庫，增加 bundle 大小與風格一致性負擔。

> **建議做法**：兩個輪播都先用 Swiper 實作，用最少的套件數滿足「單圖輪播」＋「多卡片 RWD 輪播＋觸控拖曳」兩種行為；若之後遇到 Shadow DOM 樣式客製化卡關或在意 bundle size，再評估換成 Embla。

**資料需求／待確認**：

- 輪播圖、最新訊息、工商廣告三者的資料都直接寫在首頁元件的 `.ts` 檔案內（常數陣列），圖片本身仍放前端 assets 靜態圖片檔；不走外部 JSON 檔，也不走 CMS／後端 API。更新內容時由開發者直接修改 `.ts` 檔案內的陣列後重新部署。
- 工商廣告卡片目前排序規則＝依陣列順序顯示，不做日期或其他排序；如需調整顯示順序，直接調整陣列順序即可。若未來需要「依分類」或「依到期日自動下架」等規則，需再評估擴充欄位。
- 輪播圖是否需要連結欄位，列為待確認事項（見上方「輪播圖」小節的說明）。

## 交通方式 `/traffic`

**目的**：解決「怎麼去」，並降低初次到訪者的焦慮（山區道路、停車）。

> 本節路線／班次資訊於 2026-10-02 參考 Google 地圖、大台北公車電子化系統（ebus.gov.taipei）與新北市三峽區公所官網整理，**上線前務必重新核實一次**（公車時刻表與接駁車資訊變動頻率較高，不保證長期正確）。

**版面結構**：頁面內以**頁籤（Tab）**拆成「開車」「大眾運輸」兩個分頁切換顯示，同一個路由 `/traffic`，不另開頁面；停車資訊兩個頁籤都會用到，放在頁籤外作為共用區塊，不重複塞進兩個頁籤裡。**Google Map 嵌入地圖只放在「開車」頁籤內**，「大眾運輸」頁籤不需要地圖（該頁籤的導引靠下方的 Google 地圖規劃路線按鈕，不需要再重複嵌入地圖）。

### Tab 1：開車（兩條路線＋嵌入地圖）

依出發方向不同，列出兩條建議路線，皆以**白雞停車場**為終點：

| # | 路線 | 建議開車指引 |
|---|---|---|
| 1 | **新店／安坑交流道 → 白雞停車場** | 國道 3 號安坑交流道下 → 安坑路（110 縣道）往三峽方向 → 成福橋 → 竹崙路 → 紫微路 → 白雞停車場。（北部／新店方向出發適用） |
| 2 | **三鶯交流道 → 白雞停車場** | 國道 3 號三鶯交流道下 → 復興路往三峽老街 → 台 3 線（中正路一段）→ 正義街 → 白雞路 → 紫薇路 → 白雞停車場。（桃園／中壢方向出發適用） |

- 每條路線後方放一顆「**在 Google 地圖開啟路線**」按鈕，固定帶「該交流道 → 白雞停車場」這組起訖點，讓使用者點下去就能在 Google 地圖／App 直接預覽這條路線（不是從使用者目前位置規劃，因為目的是讓使用者先看過路線長什麼樣子，再自行導航）：

  ```
  https://www.google.com/maps/dir/?api=1&origin=<交流道>&destination=<白雞停車場>&travelmode=driving
  ```

  1. 安坑交流道路線：`https://www.google.com/maps/dir/?api=1&origin=國道3號安坑交流道&destination=行修宮(行天宮三峽分宮)&travelmode=driving`
  2. 三鶯交流道路線：`https://www.google.com/maps/dir/?api=1&origin=國道3號三鶯交流道&destination=行修宮(行天宮三峽分宮)&travelmode=driving`

  > 這兩條路線的文字指引是依網路公開資訊整理，**實際路況（例如成福橋一帶是否有替代道路、會車狀況）建議上線前實際開車或用 Google 地圖街景再核對一次**，道路施工或改道都可能讓文字指引過時，但 Google 地圖按鈕本身永遠是即時路況，不會過時。

- **嵌入地圖**：兩條路線下方（或頁籤底部）放一個共用的 Google Map 嵌入地圖，標示「白雞停車場」位置，讓使用者先看到目的地長什麼樣子／在哪個相對位置。
  - **做法建議**：用 Google 地圖「分享 → 嵌入地圖」產生的 `<iframe>` 嵌入連結（`https://www.google.com/maps/embed?pb=...`）。不需要申請 API Key、沒有額度／計費問題，符合目前全站以靜態資料為主、不依賴後端服務的作法。
  - 替代方案是 Google **Static Maps API**（產生一張純靜態縮圖），但需要申請並管理 API Key、超過免費額度要計費，維運成本較高；除非有特別需求（例如要在圖上疊加自訂圖層），否則不建議優先採用。
- 山路行車注意事項（會車、坡度），兩條路線皆適用，不需要各寫一份。

### Tab 2：大眾運輸（五種搭乘方式）

- **頁籤頂部縮圖**：不放 Google Map 嵌入地圖，改放一張靜態示意縮圖（例如公車／捷運主題的簡約插畫），作為裝飾用途，純視覺標題、無地理資訊。圖片本身為靜態素材（放前端 assets），之後若路線異動也不需要跟著更新這張圖。圖片的實際製作風格（配色、插畫風格）另外在「設計風格」文件中定義，此處先確定「有這塊內容」即可。

版面上以五個小節／卡片並列呈現五種可行組合：

| # | 組合 | 搭乘方式摘要 |
|---|---|---|
| 1 | **公車** | 台北客運 **778**（三峽－白雞）。於三峽老街／三峽公車站一帶上車，終點「白雞站」下車，步行約 3 分鐘到行修宮／商場。平日、假日頭末班車皆為 05:50～19:10，為收費路線（一段票）。 |
| 2 | **免費公車** | 新北市新巴士 **F626**（紫微線）。於三峽國小一帶上車，於「行天宮白雞行修宮」站下車即達，全程免費。發車時間約 08:15／10:15／13:30／16:30／18:30（班次少，建議先查即時動態確認）。 |
| 3 | **捷運（三鶯線）＋公車** | 搭新北捷運三鶯線至「三峽站（LB06）」，出站後轉乘 778 公車至「白雞站」下車。三鶯線已於 2026-06-30 通車，三峽站鄰近三峽老街／三峽國小一帶的公車站牌，轉乘步行距離不遠。 |
| 4 | **捷運＋免費公車** | 搭新北捷運三鶯線至「三峽站（LB06）」，出站後轉乘 F626 免費巴士（紫微線）至「行天宮白雞行修宮」站下車。 |
| 5 | **新店捷運站＋免費公車** | 搭台北客運 **779**（新店捷運站－三峽一站）至「**檢查站**」站（在地俗稱「竹崙橋頭」）下車，過馬路到對向站牌轉乘 F626 免費巴士（紫微線）往白雞方向，至「行天宮白雞行修宮」站下車，不需要搭到三峽市區再轉車。 |

> **關於「新店有沒有直達車」與轉乘點選擇**：實際查了兩條路線的完整站名清單後確認：779（新店↔三峽）和 F626（三峽國小↔白雞行修宮）從「成福國小」一路到「檢查站」有一長段**共用站名**（成福國小、辭修高中、大坪新村、大同工廠、海一、海一(二)、成福活動中心、成福派出所、駱駝潭、檢查站），過了檢查站之後兩條路線才分開——779 續往大成國小、安坑方向開回新店，F626 則轉往紫微／白雞方向。所以新店到三峽這段其實是有公車直達的（779），不是空白；但**最適合轉乘的站是這段共用區間裡最後一站「檢查站」**，而不是前面任何一站——在檢查站之前轉乘等於提早下車改搭另一班一樣會經過同樣路段的公車，沒有意義；只有在檢查站轉乘才是真正「後面路段兩條路線不再重疊」的那一點。

- **點擊「778」「779」「F626」這類公車／免費公車名稱，即可開新分頁連結到該路線的官方時刻表／即時動態頁面**（`target="_blank"`），不自行維護班次資料，避免內容過時：
  - 778：`https://ebus.gov.taipei/EBus/VsSimpleMap?rid=17515&sec=0`
  - 779：`https://ebus.gov.taipei/EBus/VsSimpleMap?routeid=0400077900&gb=1`
  - F626：`https://ebus.gov.taipei/EBus/VsSimpleMap?routeid=0454062600&gb=0`（新北市三峽區公所也有對應說明頁可作備援：`https://www.sanxia.ntpc.gov.tw/home.jsp?id=2abb71766f9764ee`）
  - > 上述 ebus 連結目前顯示的是路線圖＋即時動態；是否完整涵蓋「固定時刻表」需要在真正串接前人工再確認一次畫面內容，且公車系統偶爾會改版網址結構，建議正式開發時重新抓一次連結並做失效時的 fallback（例如連不到就導向三峽區公所官網）。
- 每個組合下方補充下車後步行距離與時間（778／F626 在白雞站／行修宮站下車後，步行約 3 分鐘內可達商場）。
  - 第 5 項（779 轉 F626）額外補充：在「檢查站」下車後，兩條路線的站牌分別在馬路**對向**（往新店／往白雞方向相反），需要過馬路到對面站牌等 F626，和其他幾項「同一站牌直接換乘」的情況不同，建議在頁面文案上明確寫「過馬路轉乘」提醒使用者；確切的過馬路地點與站牌位置，上線前建議現場走一趟或用 Google 街景再確認一次。
- **每一列（5 條路線）後方再放一顆「用 Google 地圖規劃路線」按鈕**，點擊後帶使用者的目的地（白雞行修宮）資訊開啟 Google 地圖（已安裝 App 的裝置會直接跳轉 App，沒安裝則開啟網頁版），由 Google 地圖即時幫使用者從目前位置規劃路線，不需要使用者自己在 Google 地圖裡重新輸入地址搜尋。

  - **做法**：使用 Google 地圖的 Directions 通用連結（Universal Link），不需要 API Key：

    ```
    https://www.google.com/maps/dir/?api=1&destination=<目的地>&travelmode=transit&transit_mode=<交通工具偏好>
    ```

    | 參數 | 說明 |
    |---|---|
    | `destination` | 固定帶入「行修宮(行天宮三峽分宮)」地標名稱（URL encode 後代入），**不要用「新北市三峽區嘉添里白雞路155號」這個地址**——實測這個地址在 Google 地圖會導到錯誤的地點 |
    | `travelmode=transit` | 固定帶大眾運輸模式（五條路線都是，不需要分別設定 driving／walking） |
    | `transit_mode` | 依每列的組合代入偏好值，可用逗號帶多個：公車類用 `bus`；含捷運的組合用 `bus,subway` |
    | `origin` | **不帶這個參數**，留空讓 Google 地圖預設抓使用者目前位置（裝置會請求定位權限），才能真正做到「引導使用者」從所在地出發 |

  - 五條路線的按鈕連結範例：
    1. 公車（778）：`https://www.google.com/maps/dir/?api=1&destination=行修宮(行天宮三峽分宮)&travelmode=transit&transit_mode=bus`
    2. 免費公車（F626）：同上，`transit_mode=bus`
    3. 捷運（三鶯線）＋公車：`https://www.google.com/maps/dir/?api=1&destination=行修宮(行天宮三峽分宮)&travelmode=transit&transit_mode=bus,subway`
    4. 捷運＋免費公車：同第 3 條，`transit_mode=bus,subway`
    5. 新店捷運站＋免費公車（779 轉 F626）：公車轉公車，`transit_mode=bus`
  - **已知限制（待使用者理解，不是開發疏漏）**：Google 地圖的 Directions 網址參數只能提示「偏好的交通工具種類」（公車／捷運），**無法指定「一定要搭 778」「779」或「一定要搭 F626」這種特定路線號碼**——實際會規劃出哪一班車，是由 Google 當下的即時運算決定，可能和本頁列出的路線不完全一致。因此第 1、2、5 條路線的按鈕網址其實完全相同（都只能設定「公車」），真正要確認「778／779／F626 這幾班車何時發車」還是要靠前一點提到的官方時刻表連結，這顆按鈕的定位是「快速開始這個大方向的路線規劃」，不是「精準導航到這幾班特定公車」。
  - **實作建議**：這 5 條路線的資料（組合名稱、摘要文字、時刻表連結、Google 地圖按鈕的 `transit_mode` 值）結構高度相似，建議在前端寫成一組小陣列（例如 5 筆物件：`{ mode, title, summary, scheduleLink, mapTransitMode }`），而不是寫 5 份幾乎一樣的模板，之後如果交通組合有調整（例如之後三鶯線改用其他接駁路線），只需要改資料不用改版面結構。

### 詳情頁 `/shop/detail/:number`（僅 `officialWebsite` 為空的店家會觸發導向）

**路由行為**：獨立路由，非 Popup／Modal；`:number` 對應店家 `number` 欄位值。**決定（2026-10-05）**：若網址列直接輸入或分享一個不存在的 `:number`（例如店家已下架），**導回 `/shop` 列表頁**（不另外設計 404 頁面），讓使用者直接看到完整店家清單自行重新選擇，比顯示一個「找不到」的死路頁面更有用。

**版面（由上而下）**：
1. **返回列表連結／麵包屑**：頁面左上角（或頁首）放「返回商場店家列表」的連結，點擊返回 `/shop` 並恢復原本捲動位置與篩選狀態（見上方「從詳情頁返回列表」規則）。
2. **標題區**：店名（name）。
3. **圖片輪播**：`images` 陣列輪播顯示（無圖片時此區塊從缺，實務上會落到 `assets/images/placeholder.jpg` 佔位圖）。
4. **介紹內容**：`doc` 欄位的完整介紹文字（空字串時此區塊從缺，例如 mock 資料第 10 筆）。
5. **聯絡電話**：`phone` 陣列逐一列出（圖示＋號碼），陣列為空時此區塊從缺。
6. **Footer（社群連結圖示列）**：依序檢查 `fb`／`ig` 等社群欄位，**有填值的才顯示對應圖示**（無值則不顯示該圖示，不是顯示灰階或禁用狀態），點擊圖示開新分頁（`target="_blank"`）連到該連結。

**待確認**：相片輪播、完整介紹、聯絡電話顯示位置已如上定案；招牌商品／菜單、價格區間、營業時間、地圖定位等欄位目前仍不在資料結構內，是否需要補上待商場管理方提供對應資料後再議。

**開發備註**：分類 enum 與店家列表**從頁面元件抽出，獨立放在共用的 `shop.service.ts`**（而不是像首頁三區塊那樣直接寫死在頁面元件的 `.ts` 檔案內），原因是這份資料現在同時被**列表頁**（`/shop`）與**詳情頁**（`/shop/detail/:number`）兩個路由／元件共用，透過 service 讓兩邊注入同一份資料來源，避免各自維護一份陣列、資料跑掉不同步的風險；之後如果要換成 CMS／API 來源，直接改這個 service 內部的資料取得方式即可，不需重構列表／詳情頁元件本身。

## 全站共用元件

- **Header**：左側是「三峽白雞觀光商場」Logo（圖示＋文字），**整個 Logo 本身就是回首頁的連結**，不在主選單裡重複放一個「首頁」項目。右側主選單為交通方式／商場店家／周邊景點／登山資訊／商場介紹（共 5 項）。「周邊景點」是唯一的下拉選單（行脩宮外部連結＋周邊三峽景點子頁）；**商場介紹**放在最右側，以對比色或加粗呈現，取代原本的「導航到商場」CTA 按鈕。
- **Tab 元件**：交通方式頁的「開車／大眾運輸」切換使用，未來其他頁面若需要同頁切換內容可重複使用。
- **List + Detail 元件**：商場店家採「卡片列表（`/shop`）→ 點擊導向獨立詳情頁（`/shop/detail/:number`）→ 返回列表恢復捲動位置與篩選狀態」模式，店家資料透過共用的 `shop.service.ts` 注入給兩個路由的元件（見商場店家一節「開發備註」）。登山資訊**不使用**此模式，卡片點擊直接開新分頁連到外部來源網站，不經過站內詳情頁。
- **外部連結標示**：行脩宮等連到站外的連結，統一用圖示（如 ↗）＋ `target="_blank"` 標示，讓使用者清楚知道會離開本站。
- **Footer**：商場資訊（地址／電話／營業時間）、快速連結、聯絡我們（Email），版權資訊。
- **麵包屑（Breadcrumb）**：周邊三峽景點子頁、商場簡介與沿革（`/market/about`）、**商場店家詳情頁（`/shop/detail/:number`，改為獨立路由後需要）**建議加上麵包屑或返回連結，方便回到上一層；登山資訊因詳情為外部連結、不經過站內頁面，不需要麵包屑。
- **地圖嵌入元件**：可重複用於交通方式、商場介紹、周邊三峽景點等頁面需要顯示地圖的區塊。
