# 三峽白雞觀光商場 官網 — 後台管理系統（上稿後台）技術規格

> 狀態：**技術架構確認 v0.1**　最後更新：2026-10-07
> 本文件記錄後台上稿管理系統的技術選型討論與決策，供日後實作與商場管理方溝通參考。前台網站規格見 [01-網站總覽與目標](01-網站總覽與目標.md) 等文件。

## 1. 背景與需求

前台網站的店家資料、首頁輪播圖／最新消息、商場介紹設施文字等內容，目前以 mock 資料或常數陣列寫在前端程式碼內。待商場管理方提供真實資料後，需要一個後台管理系統讓非工程人員也能自行上稿、更新內容，不用每次都改程式碼重新部署。

**使用者規模**：
- 管理者（擁有完整權限）：1 人
- 上稿人員（僅需內容編輯權限）：約 30-40 人

**本階段不做**（與前台規格的排除範圍一致）：電商／金流、會員系統、評論評分。

## 2. 技術選型決策

| 項目 | 決策 | 原因 |
|---|---|---|
| 後端框架 | **Strapi**（headless CMS，Node.js/Koa） | 需求是純內容上稿（店家 CRUD、輪播圖、最新消息、設施文字），沒有特殊商業邏輯。Strapi 開箱即有上稿介面、REST/GraphQL API、圖片上傳管理，幾乎不用自己寫後台 UI 程式碼。 |
| 資料庫 | **SQLite** | 規模小（單一商場、十幾筆店家、低流量），SQLite 零維運、不用額外起 DB 服務。前提：部署平台需提供持久化硬碟（見下）。 |
| 部署平台 | **Railway** | 提供持久化 volume（SQLite 檔案不會因重啟被清掉）、Git push 自動部署、用量計費，設定成本低。 |
| CDN／資安層 | **Cloudflare**（免費方案，橘雲代理） | 補強 Railway 原生 HTTPS／基本防護之外的 WAF 與 rate limit，主要用來擋 `/admin` 登入路徑的暴力破解，設定成本約 10 分鐘。 |

### 2.1 圖片上傳限制

- **單檔大小上限 5MB**：於 Strapi upload 設定（`FILE_SIZE_LIMIT`）配置，擋掉手機原圖未壓縮、動輒 10-20MB 的狀況，適用所有 Content-Type 的圖片上傳欄位（最新消息、首頁輪播圖、日後的店家工商廣告／商店資料）。
- Strapi 內建 Upload plugin 會自動產生多種尺寸（responsive breakpoints，以 sharp 處理），前台抓圖吃優化後版本，不需維護者上傳前自行壓圖或限制解析度。

### 已評估但不採用的方案

- **自架 VPS**：長期更省錢、控制權更高，但需自己處理 SSL、備份、系統更新等維運工作。考量目前沒有時間投入維運，優先選 Railway。
- **reCAPTCHA（登入頁加防機器人驗證）**：Strapi 原生 admin 登入頁是固定元件，要插入 reCAPTCHA 需客製化 plugin，工程量與效益不成比例；且 Cloudflare rate limit 已覆蓋同一種「機器人暴力破解」威脅，不重複建設。
- **SMS OTP 兩階段驗證（簡訊發送登入密碼，不設固定密碼）**：需整個重寫 auth 流程為 custom plugin，另外要接 SMS 服務商並按則計費；且 SMS 驗證本身被視為比 TOTP App 更弱的二階段驗證方式（易受 SIM 卡掉包攻擊），業界（如 NIST）已不建議作為主要 2FA 手段。
- **SSO／Google 登入**：Strapi Community（免費）版不支援，屬於 Enterprise 付費功能。原本考慮的動機（避免處理使用者忘記密碼的客服工作）已由 Strapi 內建的自助密碼重設流程解決，故無需為此升級付費版。

## 3. 帳號與權限管理

### 3.1 三種角色與權限矩陣

後台管理的四種內容：最新消息、首頁輪播圖、店家工商廣告、商店資料（商家自身的店家資料，對應前台 `/shop` 與 `/shop/detail/:number`）。

| 內容類型 | 管理者 | 網站維護者 | 商家帳號（角色3） |
|---|---|---|---|
| 帳號管理 | 全部 CRUD | 無 | 無 |
| 最新消息 | 全部 CRUD | 全站 CRUD | 無 |
| 首頁輪播圖 | 全部 CRUD | 全站 CRUD | 無 |
| 店家工商廣告 | 全部 CRUD | 全站 CRUD | 無 |
| 商店資料（所有商家） | 全部 CRUD | 僅能**編輯**綁定的 1 個固定商家 | 僅能**編輯**綁定的 1 個固定商家 |

- 管理者：唯一擁有帳號管理權限，可建立/指派網站維護者與商家帳號、綁定其對應的商家。
- 網站維護者：對最新消息／輪播圖／店家工商廣告是全站範圍，近似「站方行銷人員」；但商店資料僅能維護自己綁定的那一個商家（不含新增/刪除，僅 update）。
- 商家帳號：僅能編輯自己綁定的那一個商家的商店資料（僅 update），不能碰其他三種內容。
- 商店資料的新增／刪除（新商家上架/下架）保留給管理者，避免維護者或商家帳號誤刪其他商家的資料。
- 帳號／角色設定僅管理者可調整：這是 Strapi 原生行為（非客製），帳號與角色管理收在 Admin Panel 的 Settings 區，預設只有 Super Admin 角色能進入，網站維護者與商家帳號兩種角色完全看不到此設定頁，不需額外開發。

### 3.2 技術實作方式

Strapi Community 版的角色權限（RBAC）是**content-type 整體層級**的（例如「這個角色可以 CRUD 商店資料這個 collection」），**不支援**原生限制「這個使用者只能碰其中某一筆固定資料」。要做到角色2、3「僅限一個固定商家」的限制，需要：

1. 在 Strapi 的 Admin User 資料結構上加一個「綁定商家」關聯欄位（relation to 商店資料）。
2. 寫一個 custom policy，在商店資料的 update 請求進來時，檢查請求者的「綁定商家」是否等於目標資料的 ID，不符就擋掉。

此為 Strapi 官方文件中有範例的常見客製模式，非大工程，但不是裝好 Strapi 就自動具備，需另外開發這段 policy。

### 3.3 其他帳號管理事項

- **密碼重設**：Strapi admin 登入頁內建「忘記密碼」自助重設流程（email 寄送重設連結），使用者自行處理，不需管理者介入。需一次性設定寄信服務（SendGrid／Mailgun 等，多有免費額度）。
- **兩階段驗證（2FA）**：評估後暫不強制導入。人數多（30-40 人）時密碼強度不一的風險確實較高，TOTP App（Google Authenticator 等）是比 SMS 更安全且免費的選項，可作為日後加強項目，非本階段必須。

## 4. Content-Type 欄位設計

後台共四種 Content-Type：最新消息、首頁輪播圖、店家工商廣告、商店資料。對應前台頁面規格見 [03-頁面內容規格](03-頁面內容規格.md)。

### 4.1 最新消息（News）

對應前台首頁「最新訊息公告」區塊（[03-頁面內容規格](03-頁面內容規格.md) 第2節）。

**列表頁**：

- 右上角「新增」按鈕，導向新增頁。
- 表格欄位：**建立日期**（系統自動產生的 `createdAt`，唯讀，不可編輯）、**消息內容日期**、**標題**、編輯按鈕、刪除按鈕。
- 刪除按鈕需二次確認（Popup 彈窗再次確認「是否確定刪除」，確認後才真正刪除），避免誤刪。

**編輯／新增頁欄位**：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 標題 | 字串 | 必填 | |
| 消息內容日期 | 日期 | 必填 | 與系統建立日期分開，可自訂（例如補登過去的公告），前台排序依此欄位，非系統建立日期 |
| 圖片上傳 | 單張圖片 | 選填 | 僅在「外部連結」欄位空白時，於前台 Popup 中顯示 |
| 內容敘述 | 文字，最多 300 字 | 選填 | 同上，僅在「外部連結」空白時於 Popup 顯示 |
| 外部連結 | 字串（URL） | 選填 | 有填值：前台標題變為可點擊連結，新分頁開啟該網址，不顯示 Popup；空白：標題點擊後開 Popup，顯示圖片＋內容敘述 |

> 沿用前台既有的 `link` 欄位邏輯（[03-頁面內容規格](03-頁面內容規格.md) 第2節），後台不改變此互動規則。

### 4.2 首頁輪播圖（Carousel／Banner）

對應前台首頁輪播圖區塊（[03-頁面內容規格](03-頁面內容規格.md) 第1節，前台已簡化為純圖片陣列，不含標題／連結欄位）。

**列表頁**：

- 僅一頁列表（不分頁），以**卡片縮圖**方式呈現每一張圖片。
- 每張卡片：圖片縮圖、編輯按鈕（可重新上傳替換圖片）、刪除按鈕。
- 右上角「新增」按鈕，開啟上傳圖片的彈窗／頁面。
- 刪除按鈕需二次確認（Popup 彈窗再次確認「是否確定刪除」），與最新消息一致。

**編輯／新增欄位**：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 圖片上傳 | 單張圖片 | 必填 | 無標題／連結欄位，與前台現行簡化版資料結構一致 |

**排序與張數**：沿用前台既有規則（[03-頁面內容規格](03-頁面內容規格.md) 第1節）——依**建立時間**排序，不提供手動拖曳排序；前台最多顯示 5 張，超過僅取前 5 張，後台不強制限制上傳數量，僅提醒維護者超過 5 張時多出的不會顯示。若日後需要手動調整輪播順序，需額外加一個「排序」欄位（非本階段範圍）。

### 4.3 店家工商廣告（Activity）

對應前台首頁「店家工商廣告」卡片輪播區塊（`home.ts` 的 `ActivityItem`）。頁面架構與最新消息相同（列表＋編輯頁）。

**列表頁**：

- 表格欄位：**標題**、**建立日期**（系統自動產生的 `createdAt`，唯讀）、編輯按鈕、刪除按鈕。
- 右上角「新增」按鈕，導向新增頁。
- 刪除按鈕需二次確認（Popup 彈窗），與最新消息、首頁輪播圖一致。

**編輯／新增頁欄位**：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 標題 | 字串 | 必填 | |
| 圖片上傳 | 單張圖片 | 必填 | |
| 活動開始日期 | 日期 | 必填 | |
| 活動結束日期 | 日期 | 必填 | |
| 簡述 | 文字 | 必填 | 卡片上直接顯示的短文（對應前台 `brief`） |
| 內容 | 文字 | 必填 | 點擊卡片開 Popup 顯示的完整敘述（對應前台 `content`） |

> 沿用前台既有的 `ActivityItem` 資料結構，後台不改變前台卡片／Popup 的顯示邏輯。

### 4.4 商店資料（Shop）

對應前台店家列表／詳情頁（`shop.service.ts` 的 `Shop` 與 `ShopProduct`）。這是唯一會被角色2（網站維護者）、角色3（商家帳號）碰觸、但限定在自己綁定那一筆的內容類型（見第 3.1 節權限矩陣）。

**列表頁**（管理者視角，可見全部商家）：

- 依商家 **number** 排序列出所有商家。
- 表格欄位：商家編號（`number`）、店名、分類、編輯按鈕、刪除按鈕。
- 刪除需二次確認（Popup），且僅管理者可執行（角色2、3僅有 update 權限，見第 3.1 節）。
- 角色2、角色3登入後僅能看到／編輯自己綁定的那一筆，不會顯示完整列表（實作細節待後續確認，暫定直接導向該筆的編輯頁，略過列表頁）。

**編輯頁欄位**：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 圖片上傳 | 最多 2 張圖片 | 必填 | 現有 mock 資料部分店家有 3 張圖片，需於正式上線前整理至 2 張以內 |
| 店名 | 字串 | 必填 | |
| 分類選擇 | 多選（餐飲／小吃／品茶／農特產／命理／服務） | 必填 | 對應前台 `ShopCategory` enum，一間店可選多個分類；後台實作為獨立分類 Collection Type 多對多關聯，見第 4.5 節 |
| 店家介紹 | 文字，最多 500 字 | 必填 | 對應前台 `doc` |
| 電話1 | 字串 | 必填 | |
| 電話2 | 字串 | 選填 | 最多兩支電話，取代原陣列結構 |
| LineID | 字串 | 選填 | 對應前台 `line` |
| FB | 字串 | 選填 | 對應前台 `fb`，沿用保留 |
| IG | 字串 | 選填 | 對應前台 `ig`，沿用保留 |
| 官網連結 | 字串（URL） | 選填 | 對應前台 `officialWebsite`，沿用保留 |

> 不新增 email 欄位；聯絡資訊維持電話（拆成電話1/電話2）、LINE、FB、IG、官網，與前台現有欄位一致。

**商品與服務（頁面最下方子列表）**：

- 後台實作為商店資料底下的 Component（非獨立 Collection Type），見第 4.5 節。
- 列表欄位：商品名稱、價格、簡述；點擊商品名稱開 Popup 編輯該筆。
- 「新增商品」按鈕，商品總數上限 **20 個**。
- 刪除商品需二次確認（Popup），與其他刪除行為一致。

**商品 Popup 編輯欄位**：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| 圖片上傳 | 單張圖片 | 必填 | |
| 商品名稱 | 字串 | 必填 | |
| 價格 | 字串，最多 10 字 | 必填 | 型別為字串（非數字），可填「NT$600 / 150g」等含單位格式，對應前台 `price` |
| 簡述 | 文字，最多 100 字 | 必填 | 對應前台 `desc` |

### 4.5 Content-Type Builder 實作細節

Strapi 原生欄位型別對兩處規格支援度不足，需要在 Content-Type Builder 階段決定對應做法：

- **商品與服務（products）**：採用 **Component（Repeatable Component）**，掛在商店資料（Shop）底下，不另開獨立 Collection Type。理由：商品永遠依附單一商店編輯、上限 20 筆，用 Component 讓資料跟著商店走（刪商店即連同商品一起刪除），不會有被誤關聯到其他商店的風險。
- **分類選擇（type，多選）**：Strapi 的 Enumeration 欄位預設僅支援單選，不符合「一間店可選多個分類」的需求。改為獨立開一個**分類（Category）Collection Type**，與商店資料建立**多對多（Many-to-Many）關聯**。好處是分類清單本身也能在後台直接管理（新增/調整分類名稱），不需要改程式碼。
- 「圖片最多2張」「商品總數上限20個」這類數量上限，Strapi 介面無原生硬性檢查，需於實作階段寫 lifecycle hook 做 custom validation；此為實作細節，不影響上述欄位型別決策。

## 5. 前台串接方式

- **API 權限**：Strapi 預設新建 Content-Type 的 Public（未登入）角色沒有讀取權限，需到 Settings → Roles → Public，將四種 Content-Type 的 `find`／`findOne` 權限打開，前台才能不帶 token 直接讀取。
- **抓資料方式**：前台（Angular 22、signal 風格）改用 `httpResource` 呼叫 Strapi 的 REST endpoint（如 `/api/news`、`/api/activities`、`/api/shops`、`/api/banners`），取代現在寫死在 `home.ts`／`shop.service.ts` 的常數陣列。
- **圖片網址**：Strapi 回傳的圖片欄位是相對路徑（如 `/uploads/xxx.jpg`），前台顯示時需自行補上 Strapi 的網域前綴。
- **渲染模式決策**：原本 `app.routes.server.ts` 的路由是 `RenderMode.Prerender`（build 時烤入靜態 HTML），改接即時 CMS 資料後，**改為 `RenderMode.Server`**——每次請求時才呼叫 Strapi API 並在伺服器端渲染成完整 HTML 再送出。Prerender／Server 兩者送出的 HTML 都是完整渲染好的，SEO／爬蟲（含 Googlebot）看到的都是真實資料，差別只在「渲染時間點」，故改用 Server 模式不影響 SEO。代價是每次請求都多一次打 Strapi API 的延遲，此案流量小應無影響；**先採用 Server 模式，若日後流量顯著成長再評估改回 Prerender 或導入快取層**。
